# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `pnpm install` — install dependencies (Node ≥ 22, pnpm 10).
- `pnpm build` — emit `dist/` via `tsc -p tsconfig.json` (also compiles tests).
- `pnpm typecheck` — type-only check, no emit.
- `pnpm lint` — runs `scripts/lint.mjs`: bans tabs and trailing whitespace, requires trailing newline on `.ts/.md/.json/.mjs/.html` files (skips `dist`, `node_modules`, `.tmp`, `.out`, `.omx`, `.bg-shell`, `prds`, etc.).
- `pnpm test` — builds, then runs the four node:test suites sequentially.
- `pnpm check` — `lint && typecheck && test`. Run this after host workflow changes (per `AGENTS.md`).

Tests use `node:test`. To run one suite: `pnpm build && node dist/tests/parser.test.js`. To run a single named test inside a suite: `node --test --test-name-pattern="<substring>" dist/tests/parser.test.js`.

CLI invocation (after build): `node dist/src/index.js generate <spec.md> [--template <id>] [--app-name <n>] [--force] [--skip-validation] [--stdout log|dashboard]`. `-g` and `-v` are short aliases for `generate` and `validate`. `--resume <session-id>` resumes a session; `validate <session-id> [--phase plan|generate|auto]` re-runs validation. If launched under Bun, `src/index.ts` re-execs under Node — runtime proxy support requires Node.

## High-Level Architecture

`app-builder-v2` is a CLI that turns a Markdown PRD into a runnable app scaffold. The host (this repo) drives a staged workflow; the LLM work happens inside `deepagents` stages whose prompts come from a selected **template pack** under `templates/<id>/`.

### Host workflow (gated phase machine)

Phases: `plan → plan_repair? → generate → generate_repair? → validation → complete` (see `WorkflowPhase` in `src/lib/types.ts`). The contract is:

- The host orchestrator (`src/lib/generator.ts`) owns sequencing, retries, and gates. **Code generation must not start until host validation of `.deepagents/plan-spec.json` passes.** `plan-spec.ts` defines the Zod schema; `validatePlanSpec` is the gate.
- Each phase has a configurable retry budget (`templateRepairRetries`) and an optional repair lane that uses a different prompt to fix the previous attempt's output rather than restart.
- `text-generator.ts` (`DeepAgentsTextGenerator`) is the runtime adapter: it composes the system prompt for each stage, wires `deepagents` streaming, and parses the structured result into `PlanResult` / `GeneratedProject` / `ReferenceMarkdownConversionResult`.
- `terminal-ui.ts` renders the workflow board / log lines. Stage labels surface in tests — keep `tests/env.test.ts` aligned when UI flow changes.
- `interactive-runtime-validation.ts` runs the generated app's dev server and replays interaction coverage (`mini-app` template enables this; `full-stack` uses command-only validation).

### Sessions and artifacts

Each `generate` run creates `.out/<sessionId>/` (session id = UUID). The generated app is written at the session root; the `.deepagents/` subdirectory is the host's audit/context store. Authoritative artifact paths are pinned in `session-policy.ts` and surfaced through `OutputWorkspace`/`TextGeneratorRuntime` in `types.ts`:

- `.deepagents/source-prd.md`, `prd-analysis.md`, `generated-spec.md`
- `.deepagents/plan-spec.json` + `plan-validation.json` (host gate)
- `.deepagents/interaction-contract.json`, `generation-validation.json`
- `.deepagents/runtime-validation.log`, `runtime-interaction-validation.json`
- `.deepagents/<phase>-system-prompt.md` (snapshots of the prompts used)
- `.deepagents/config.json`, `metrics.jsonl`, `error.log`, `trace.log`
- `template-lock.json` (hash + version of the template pack used)

The `.deepagents/AGENTS.md` written into each session is generated by `buildSessionPolicyDocument()` — modify the policy text there, not in the output.

### Template packs (`templates/<id>/`)

Two packs ship: `full-stack` (Next.js + Prisma + SQLite + auth/CRUD scaffolding) and `mini-app` (minimal Next.js shell). `template.json` declares: `phases.<plan|planRepair|generate|generateRepair>` (prompt path + effort), `repairRetries`, `runtimeValidation` (steps the host shells out to verify the generated app), and optional `interactiveRuntimeValidation`. `template-pack.ts` loads, hashes, and stages the pack into the session's `.deepagents/`. Default template id is `full-stack`.

Per-template directories: `prompts/` (phase system prompts), `references/` (architecture docs copied into the session), `skills/` (optional agent skills), `starter/` (optional starter files copied into the generated app root).

### Model role configuration

`model-config.ts` resolves three roles: `plan`, `generate`, `repair` (repair covers both plan-repair and generate-repair). Each can be overridden independently via env: `APP_BUILDER_<ROLE>_MODEL`, `APP_BUILDER_<ROLE>_BASE_URL`, `APP_BUILDER_<ROLE>_API_KEY`. `APP_BUILDER_API_KEY`, `APP_BUILDER_BASE_URL`, `APP_BUILDER_MODEL` are global fallbacks. Model strings use the `provider:model` form (default `openai:gpt-4.1-mini`). `.env` is loaded automatically from cwd at CLI startup (`env.ts`).

## Working in this repo

- `AGENTS.md` is the binding workspace policy. Key points it asserts: keep host orchestration vs. template execution explicit; do not let generation proceed before host validation; `prds/` is user content — never lint, format, or auto-edit it (`scripts/lint.mjs` already excludes it).
- When adding a brand-new host phase (e.g. a `deploy` lane after `generate`), use the `host-phase-builder` skill at `.codex/skills/host-phase-builder/SKILL.md` — it enumerates the file surface (types, generator, output-workspace, terminal-ui, template.json, prompts, tests) that must move together.
- Host code is concentrated in a small set of files; touching one usually implies touching its peers: `generator.ts` (state machine), `text-generator.ts` (deepagents runtime + prompt composition), `terminal-ui.ts` (board/logs), `types.ts` + `plan-spec.ts` (contracts), `output-workspace.ts` + `session-policy.ts` (artifacts), `template-pack.ts` (template loading/staging), `interactive-runtime-validation.ts` (post-generate runtime checks).
- Tests are large and integration-leaning — `generator.test.ts` covers the full state machine including retry/repair paths. When changing phase behavior, exercise both success and retry paths.
